# 首期OA业务验收：会话、自动绑定与流量隔离审批单

日期：2026-10-16。**PROPOSED / NOT_APPROVED**。本文提供可直接决策的候选，不是启用指令。当前企业门禁全部保持；本轮无真实登录。

## 1. 建议决策

首期使用local_approved + authorization准入，Refresh API不续期。本地会话和Access到期后必须重新SID OIDC授权，仍需SID证明已有SSO下重新检查准入。首期只支持KnowHub本地退出，不宣称SID统一登出。

建议首次受控业务验收选择 **方案M：10分钟**；安全负责人可选择S或另定值。四项数字都仅是候选，尚未写入服务器。

| 候选 | Access TTL | 本地绝对期限 | 空闲期限 | 准入结果最大可用期 | 用户体验与风险 |
| --- | --- | --- | --- | --- | --- |
| S：最短验收 | 5分钟 | 5分钟 | 5分钟 | 5分钟 | 活跃用户至少约每5分钟重新授权；适合快速验证，较易在操作中到期；本地残留窗口较小 |
| **M：推荐首次验收** | **10分钟** | **10分钟** | **10分钟** | **10分钟** | 给登录、权限、退出检查留出时间；活跃用户约每10分钟重新授权；不是最终全员产品策略 |
| L：体验优先 | 30分钟 | 30分钟 | 10分钟 | 30分钟 | 活跃用户最长约30分钟重新授权，空闲先失效；本地停用残留上界较大，不建议首次先用 |

刷新页面、切租户或业务访问不能移动绝对期限。实际期限可能受准入有效期、撤销及安全校验更早限制。空闲期限取决于服务端可认定的活动，不保证后台轮询等同于人工使用；验收需包含该边界，不能宣称用户无操作一定精确在10分钟退出。

## 2. 停用与准入责任边界

已确认：RJGH稳定唯一不回收，RJEMAIL可信且属于当前员工；SID授权阶段拒绝无效员工。不再重复索要这些事实。

仅需SID回答：

1. 停用到所有节点拒绝新authorize的最大延迟 **D** 及起算点。
2. 已有SID SSO时再次authorize是否仍检查员工有效性，停用后旧SSO是否还能取code。
3. 停用前未兑换code是否失效，其最长有效期 **C**，兑换时是否再检查准入。

当前三项均未取得正式边界，不从Token200或Discovery推断答案。若SSO复核得到保证，候选风险评估为 **D+C+本地绝对上限**，另计在途长请求/流、跨系统时钟等边界；D或C未知就不能签成可量化风险。SSO可无限重复获code时，短KnowHub会话不构成有效上界，必须停止放行设计。

## 4. 自动绑定与撤销批准范围

允许的候选范围：可信RJEMAIL唯一命中active普通账号，issuer+RJGH长期绑定并核对sub；不创建用户、不迁移原user_id/tenant/ACL。高权限、重复邮箱、冲突、停用、撤销身份不自动绑定；后续邮箱变化不重新接管其他账号。

Session为服务端安全随机ID，不以工号/sub/邮箱/jti伪造外部SessionIndex。Access必须受本地Session检查；授权准入模式禁止用Refresh维持登录。现有同期限refresh记录如用于SwitchTenant，只能在原绝对期限内消费/轮换，不能据其存在宣称Refresh续期开放。

退出撤销当前设备会话；绑定撤销覆盖该身份所有设备；管理员可按受控手册定向撤销。内部能力不等同已验收管理页面：必须指定有权执行的人、保护清单及运行手册，在真实放行前用独立合成会话验证。仅关开关不能作为已发Token失效的验收证据。

## 5. 单次真实验收的人员与流量隔离（强制门禁）

**全局自动绑定开关没有单用户白名单。** 一个合格测试账号、专用浏览器或“大家不要点”都不足以证明其他人不能触发绑定。

建议审批一个测试机短维护窗口，由测试运维实施并证明：

- 只允许指定测试工作站/受控隧道来源访问本次认证入口与callback；排除未授权局域网、代理、IPv6和其他入口。工作站由指定员工使用，停用该窗口其他操作者。
- 覆盖Frontend80、直接APP8080及其他反向代理入口；不能只限制80而留下8080直达。保留合法Frontend到APP内部访问及必要健康检查/SSH。
- 不修改生产。选择测试机现有可信网关/主机网络控制方案时另批具体规则，先保存回滚。Docker发布端口可能不经过简单UFW入口限制，必须按实际Docker转发链测试，不能仅凭规则看似存在就PASS。
- 启用真实门禁前，从获准来源确认可达、未获准来源确认不可达，并记录时间、覆盖端口/入口、规则有效性布尔值。无法提供第二来源证据时标为NOT_VERIFIED，不开始真实事务。
- 期间冻结账号/成员/权限及其他认证测试，核对只有批准普通账号满足策略，但这只是额外保护，不能替代流量隔离。
- 规则丢失、发现其他登录流量、SID/撤销负责人离线或窗口超时立即停止放行；恢复protocol_only及绑定门禁、定向撤销残留会话，再解除临时隔离。

本轮**没有配置或验证这些隔离规则**。不得为了验收擅自更改测试机防火墙/网关；需用户批准实施与回滚范围。若不能实施可靠隔离，必须另审账号级限制后再测试，不能直接开放全局策略。

## 6. 放行操作卡与通过标准

前提：SID三项回答归档、本审批单签署、[普通账号与资源准备](SOURCEID_ORDINARY_TEST_ACCOUNT_PREPARATION.md)完成并留存保护基线、流量隔离实测通过，用户再批准一笔真实事务。

1. 备份受保护配置，固定现有APP431226c3b/UI1ba24ef5f及DB3027，记录原门禁。不得恢复raw、重构核心或重复迁移。
2. 在获批窗口加载成套local_approved、authorization、四项批准期限、无Refresh、真实政策引用与自动绑定配置；完整开关表沿用 [启用计划](SOURCEID_REAL_LOGIN_ACTIVATION_PLAN.md)，不是只关protocol_only。
3. 受控浏览器的页面/API/callback都进入打包机真实业务实例，正常TLS、state、nonce、RS256不变。现有诊断有30分钟预算，应在配置加载后的有效窗口开始；不足则停，不靠反复登录取证。
4. 员工点击一次OA：SID准入 → OIDC逐阶段PASS → RJEMAIL唯一命中原用户 → issuer+RJGH绑定且sub一致 → localSession → Portal → auth/me200。新code仅兑换一次。
5. 保护基线比较原user_id、tenant、角色、ACL均相同；非空合成内容实际可读、存在的越权对照资源拒绝；没有新重复用户或权限提升。HTTP200或Portal页面本身不足以算成功。
6. 本地退出后旧Access/auth/me拒绝。Session到期、无Refresh、撤销、第二次RJGH登录等复用已有Mock或另批独立事务；不能用一笔真实会话声称覆盖全部互斥分支。
7. 任何401、验签失败、冲突、崩溃或隔离异常均立即停止、不重试；保留安全Trace。历史signature问题独立交SID核查，不放宽校验。
8. 恢复原企业门禁与批准的OIDC/诊断状态，定向撤销测试Session/派生Token，核对服务与权限；再撤销临时网络隔离并关闭浏览器/隧道。数据清理另批，保留审计。

## 7. 可直接回复的审批内容

安全负责人需明确：选择S/M/L或四个自定值、无Refresh、D/C与长请求风险接受上限、真实审批引用及复审时间。

产品/账号负责人需明确：一个测试员工和目标空间、viewer或contributor、账号/资源准备范围、异常拒绝规则、权限基线与数据清理人。

测试运维需明确：隔离规则实施方案、获准/拒绝来源验证、维护窗口、回滚及定向撤销操作人。

SID管理员仅补D、SSO再授权复核、C；不重复确认RJGH/RJEMAIL/准入方式。上述齐备后再请求用户批准一次真实业务验收，当前不启用。
