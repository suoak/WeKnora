# 企业归属批量维护方案

此流程覆盖全部角色。管理员没有独立审批/登录入口；独立历史归属证据是所有账号相同的安全条件。

## 数据来源和输入

数据负责人提供受保护的权威批次，不需要员工逐个手写名单。每个现有账号对应：issuer、稳定RJGH、可信企业邮箱、历史账号归属证据引用、来源引用、单调revision、verified_at、valid_until、active/disabled准入状态、实际政策引用。user_id可省略：工具先按已有issuer+RJGH查原user_id，首次再在数据库按规范化唯一邮箱只读join；不会创建用户。

**当前企业邮箱归属不等于历史KnowHub账号所有权。** 来源必须能够确认该员工确实拥有对应旧账号，覆盖邮箱重新分配、账号创建/转交历史和员工变动；不能把一次OIDC成功或当前目录邮箱匹配当成历史证明。数据负责人无法确认者不进入active批次。

不是要求管理员每人单独申请，而是对同一可信数据集进行一次统一审核和批量维护。SourceID绑定按原机制完成，保留user_id、全部成员/管理标记及ACL。

## 工具行为

`sourceid-ownership`默认dry-run；`--apply`才提交，`--actor`使用获授权操作人引用。数据库DSN由受保护进程环境提供，记录从stdin输入，不放命令参数、Git、CI、镜像或日志。不接收SID Secret/Token，不打印行内容、RJGH、邮箱或user_id；输出仅rows/changed/unchanged/rejected/applied计数。

输入是逐行JSON，64KiB限制作用于**单条记录**，没有总记录数上限。1000/10000行流式测试覆盖；实际吞吐与内存受操作环境约束，不代表无限资源。CLI批内防冲突索引随批次规模占用内存，可由运维分批执行，不构成全员人数限制。

protectedRow定义位于 `cmd/sourceid-ownership/main.go`。真实输入只由受保护渠道准备；不在普通报告放入真实示例。每行事务及版本保护允许重放；同版本内容变化拒绝，PostgreSQL微秒时间精度已规范化，避免相同来源事件误判不同。

应用/CLI使用禁用SQL输出的仓储连接，错误仅返回固定类别；归属模型禁止JSON序列化。PostgreSQL自身的错误DETAIL/语句/绑定参数日志是独立运维边界，正式导入前必须对专用角色/环境审核日志策略、访问控制与保留期限，避免原始输入进入普通数据库日志。本轮CI仅有合成数据，不能声称已验证生产数据库日志脱敏；不擅自修改生产全局日志配置。

## 同步规则

| 事件 | 行为 |
|---|---|
| 可信历史账号首次批量核验 | 仅写归属证据，不创建SID身份/Session |
| 员工新增且KnowHub账号已存在 | 唯一可信匹配后加入证据批次 |
| 员工新增但没有KnowHub账号 | 拒绝此行进入异常/JIT待批准流程，不自动开户 |
| 已绑定员工邮箱变化 | 优先稳定RJGH原user_id，原权限不变，不匹配另一账号 |
| 尚未绑定且邮箱/历史归属变化 | 重新提供可信证明；账户当前邮箱唯一且与证据一致才可首次关联 |
| 停用/撤销归属 | disabled增量 + 事务撤销该issuer/user企业Session及Token |
| RJGH/user_id归属转移 | 自动更新拒绝，统一异常复核，不回收身份 |
| 绑定已撤销后源再次active | 绑定撤销墓碑仍拒绝，不能由同步自动重绑 |
| 批次缺失记录/源不可用 | 不凭缺失删除；记录新鲜度到期后安全拒绝 |
| 单行冲突/错误 | 该行回滚，其他有效行可提交；非零退出与汇总告警 |

来源定时任务应使用既有企业受控调度，最小数据库权限，失败汇总告警、可重放队列与实际延迟监测。本轮没有虚构HR/SID接口或自动运行真实同步任务；正式连接器须根据实际来源契约实现。

## 最小外部配合

1. 指定权威数据集、负责人、授权范围和安全交付渠道。
2. 提供RJGH↔可信邮箱↔历史账号归属的批量依据，标识不可确认/重新分配记录。
3. 明确active/disabled是何种准入授权、事件revision、更新时间及最大同步/停用延迟。
4. 确定完整批次与增量规则、删除/停用事件、失败恢复和有效期；给出实际政策/证据引用。

不再重复确认已明确的RJGH稳定不回收或RJEMAIL由SID验证。当前没有可证明完整历史归属的企业数据源，因此没有导入真实记录、生成真实名单或推测员工编号。
