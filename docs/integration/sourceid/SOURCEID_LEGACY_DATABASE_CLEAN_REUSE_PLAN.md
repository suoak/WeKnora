## 1. 数据来源与目标

使用原 `weknora` schema79 数据库和对应文件的干净快照，不使用带合成邮箱、Mock RJGH、审核/身份、对照空间的离线验收副本 `pgdata`。

已保存干净源快照：`/home/aqyfzx/ai/knowhub-legacy79-rehearsal-20261016/private/database79.dump` 与 `private/files.tar`。它们采自原库、未经过Mock改写，目录0700/文件0600。既有快照适合恢复预演；正式切库前应对比源数据变更情况，必要时在批准的写入冻结窗口重新制作成对快照，不能默认旧快照包含之后的写入。

建立新的独立数据库和文件存储，名称、端口、目录、容量与保留期限在实际执行单中固定。保留当前 `knowhub-sourceid-business` 3027库与数据卷，以及原79库和文件卷，禁止覆盖、合并或删除。

## 2. 数据库和文件的对应关系

原库有效内容：1个KB、3份已完成解析文档、2717条非空有效分块及2717条embedding。迁移必须保留原ID和外键，不重新导入创建新用户或新知识库。

文件链路是 `knowledges.file_path` 的 resource://句柄 → `resources.handle/physical_path/storage_backend_id` → 本地或带storage://范围的local://路径 → 原 `weknora_data-files` 中实际文件。仅复制数据库不能保证原文读取；不能直接把句柄拼成文件名。

恢复文件到新卷，校验文件字节、原resources/resource_bindings及KB存储后端对应关系。先只读挂载验收；正式允许写入时仅改新文件卷，原卷始终保留。切库执行单必须绑定数据库与文件快照的同一代次，避免只回数据库却继续使用另一代文件。

## 3. 干净恢复与迁移

1. 先建无外网、无发布端口的恢复环境，并禁用APP、连接器和外部任务，导入schema79快照。
2. 使用已验证的 `pg_restore --clean --if-exists --no-owner --no-acl`，目标仅为新库，核对版本79 clean。
3. 使用固定受验APP的标准migrate执行完整79→3027，45个up脚本，不force、不跳003025/003026、不在原库执行。
4. 验证3027 clean。实际扩展版本须单独核对，已有验收为pg_search0.22.2/vector0.8.1；不能因为003007编号存在就声称扩展已升级。
5. 迁移后验证索引有效性、分块/embedding引用和原文档读取，再启动受控APP。

## 4. 账号、权限与凭据

受保护进程保留原user_id、tenant_id、账号active/管理标记、成员角色及状态、组织角色、KB creator/租户/共享权限、资源归属与绑定的私有基线；公开报告只输出一致性结果。

当前3027库中的viewer与原管理员不是同一账号，不合并同邮箱用户、不改原管理员角色、不复制Mock身份。全角色自动关联必须依据真实可信RJEMAIL及RJGH/sub一致性，仍保留冲突与撤销检查。

新目标启用前的凭据处理应另获确认：

- 原会话及auth_tokens全部撤销，不把历史JWT继续视为有效登录态。采用新的受保护JWT签名密钥，验证旧令牌无效；如原密钥被其他测试系统共享，也不能把旧密钥带入新目标。
- 旧tenant_api_keys及用户MCP/API Key默认撤销；逐项审核使用者和范围后通过正常业务流程重新签发，不导出原密钥供重放。
- 系统/连接器/模型/存储凭据必须按清单恢复与轮换。若采用新SYSTEM_AES_KEY，旧加密配置可能不可解密，应由受保护流程重新录入，不能把“原配置行仍存在”当配置可用。
- 本地密码是否保留有效需明确审批。默认恢复目标先禁用密码认证；需要恢复原本地登录时，由受保护流程执行定向重置或批准兼容方案，不向Agent提供密码/哈希。
- OIDC协议及绑定/会话门禁继续关闭；真实SID凭据用现有安全流程注入，不把隔离Mock CA、SSRF白名单或合成政策带入。

以上清理只在新目标执行，不撤销或改写原79库及当前3027库的凭据。撤销后不可依靠复制旧令牌作为验收方式。

## 5. 模型与完整RAG后续验收

已通过的是原文件业务读取与已有向量真实APP召回，不代表新查询embedding、BM25、重排、答案生成都通过。

正式模型验证先明确允许调用的模型供应方、网络目的地、模型ID、向量维度、费用边界、内容使用范围及是否允许将原知识片段发送给该模型。凭据仅由受控进程加载，不写日志、Git或报告。

分层验收：文件与元数据读取 → 已有向量召回 → BM25实际查询 → 获批embedding生成与原向量空间一致性 → 可选rerank → 完整RAG流式回答及引用。不匹配维度或embedding模型版本时不得默认重建全部索引，先制定副本重索引和回滚方案。

用原管理员验证其合法管理范围，并用独立普通账号验证实际存在且无成员/共享授权的跨空间资源拒绝。不得用随机不存在ID代替权限验收。公开记录状态、计数和一致性，不输出文档正文或员工数据。

## 6. 维护窗口与写入冻结

建议安排专门测试维护窗口，开始时间和最长中断由负责人批准。时间估算以本次全链隔离验收为参考，不能预先承诺未经计时的固定切库时长。

窗口内：确认所有实际入口及客户端 → 让默认APP停止新写入（只停止APP不足以阻止已公开的其他服务，需核对所有写入方）→ 保持后台同步关闭 → 制作当前3027库最新回滚备份及对应文件快照 → 重新校验干净恢复目标与源代次 → 单独批准切换DB/文件配置 → 仅按批准范围重建APP → 完成无凭据/本地业务验收 → 再决定是否恢复写入。

不得临时把DB_HOST指向验收用Mock副本；不能把本次APP镜像升级当作切库配置审批。

## 7. 回滚与新写入处理

保留切换前的APP配置、固定镜像、原DB/文件目标及所有卷。失败时关闭新企业会话/绑定放行，先停止写入，恢复获批的旧DB/文件组合和APP配置；oauth_form保持不变。

若新目标已经产生用户写入，先保存新目标快照并审查差异；是否回填、导出或舍弃测试写入必须由负责人决定，不能直接覆盖或回滚而丢失数据。身份审核、绑定和会话审计应保留并按正式撤销流程处理，不以删表回滚。
