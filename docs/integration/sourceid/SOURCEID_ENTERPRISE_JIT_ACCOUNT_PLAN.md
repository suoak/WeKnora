# 新员工JIT开户评估

**可设计支持，但当前候选未实现、未批准。** `SOURCEID_JIT_ENABLE=false`；设置true会拒绝普通SSO业务政策，不能静默开通。现有账号自动关联不等待JIT开发，也不把无匹配/冲突视为可以开户。

## 必需边界

1. 严格OIDC及可信企业身份/准入条件通过；普通SSO残余风险政策已批准。
2. 权威来源明确授予该新员工开户资格、可信邮箱和稳定RJGH，且并非旧邮箱重新分配后的账号接管。
3. 先查既有绑定，再查全部规范化邮箱/身份冲突。已有账号走统一原账号关联；重复、停用、撤销或归属不明时拒绝，不降级JIT。
4. 新员工确实没有KnowHub账号，独立JIT产品/安全政策批准，才可事务开户。

## 复用和必要扩展

复用现有业务 `Register(...TenantProvisioningTenantless)` 能力，不直接SQL建用户，不生成个人owner空间，不修改全局注册策略。默认无系统/组织/跨空间管理员标记，不加入任何既有敏感空间，原权限不能从邮箱或身份字段推导。

当前归属证据表要求已有user_id，不能用于声明不存在账号的员工已经完成开户。JIT需要另行完成可为空user_id的新员工授予状态/数据迁移设计，或权威源受控开户授权适配，再由事务一次性填入新user_id并建立唯一身份；不能把现有NOT NULL/FK取消后就认为安全完成。

应在统一业务事务中锁定issuer+RJGH授予、复核全局唯一邮箱、调用tenantless注册、建立身份与审核审计，再签发同一Access-only Session。并发开户只产生一个user_id，失败全部回滚；异常不创建用户。

无空间用户的Portal/空状态及后续邀请授权需要验收，不能为了显示知识库而加入owner空间。现有登录代码认可tenantless身份，但业务页面和需要租户的API仍需完整空状态测试。默认普通账号，后续由正常邀请/授权流程赋予范围，不默认继承他人知识库。

## 后续验收及批准

需覆盖无旧账号开户、已有账号不重复创建、邮箱回收、撤销/停用、并发、注册失败回滚、零默认KB权限、多空间后续邀请及无Refresh。启用必须有独立JIT政策引用、来源、新员工默认体验和负责人确认。

本轮交付为分析方案，不包含“新员工已可JIT登录”的完成声明。生产全员现有账号接入与未来新员工自动开户分别发布。
