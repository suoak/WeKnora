# 全员接入：权威归属数据对接清单

更新日期：2026-10-17。公司全员接入，所有部门与角色使用同一数据规则；不要求员工逐人配置 JSON，不为管理员设置单独登录或绑定申请。RJGH 稳定唯一不回收、RJEMAIL 由 SID 验证属于员工，继续视为已确认产品输入。事业部范围或组织字段资料不再是准入输入。

## 还缺少的真实数据

数据负责人一次性核验现有 KnowHub 账号的历史所有权，提供 issuer、RJGH、可信企业邮箱，以及能够证明该员工拥有历史账号的独立依据。当前目录邮箱归属或当次 OIDC 成功不能单独证明旧账号归属；邮箱重新分配、转交和无法确认的记录必须标为异常。

批次字段与受保护 stdin 的实际程序结构一致：

| 字段 | 要求 |
|---|---|
| issuer | 正式可信 SID Issuer；不可由未审查客户端自由指定 |
| employee_no | 已确认稳定的 RJGH |
| email | 规范化后用于首次精确匹配的可信企业邮箱 |
| user_id | 可省略；工具只读查原绑定/唯一邮箱取得，不创建用户 |
| ownership_ref | 真实历史账号归属证明引用，不能由登录结果反向生成 |
| source_ref | 实际权威来源及批次/事件引用 |
| policy_ref | 已批准的统一归属政策引用，与 APP 配置一致 |
| status | 受控来源授予或撤销此账号归属准入的 active/disabled；不是猜测 UserInfo 员工状态字段 |
| revision | 每个身份严格递增；同版本内容不可变化 |
| verified_at | 来源实际核验时间，不能在每次上传时无依据重置为现在 |
| valid_until | 来源证明的明确有效截止时间 |

真实批次不进入 Git、CI、镜像、命令参数、普通报告或日志。指定数据负责人、操作负责人、审批人、安全交付渠道和异常处理负责人，实际填写后归档；本报告不伪造姓名或批准编号。

## 接口与增量要求

目前没有正式 HR/SID 目录接口契约，未实现或运行真实同步连接器。由负责人提供受保护批次，现有 CLI 可先完成 dry-run、汇总审查、批准后 apply 和幂等重放。

未来接口或批量交付必须明确：认证与最小权限、传输加密、分页/增量游标、全量快照代次、事件顺序与重复处理、停用/撤销事件、删除语义、补发与重放、部分失败恢复及可监测的最大延迟。缺失一行不等于停用，不因不完整快照直接批量删除。

## 可执行批量流程

1. 在受保护进程中加载 DSN，受保护数据经 stdin 输入 `sourceid-ownership`；默认 dry-run，不写入数据库。
2. 汇总仅输出 rows/changed/unchanged/rejected/applied。失败返回非零；有冲突时先阻止该账号 apply，其他已核实账号不受角色影响。
3. 业务/数据负责人核验冲突与历史归属后，单独批准 apply；每行事务提交，有效行不因其他行失败整体回滚。
4. 同版本同内容重放不产生重复归属/审计；修订需递增 revision。权限、user_id、成员关系和 ACL 不由工具修改。
5. 定期导出安全计数和失败类别，异常明细只能在独立受保护工作流查看。CLI 当前不输出逐行敏感冲突报告，也不自动修复历史身份冲突。
6. 正式真实导入前审核 PostgreSQL 语句、错误 DETAIL、参数日志、备份访问和保留期限；应用关闭 SQL 日志不等于数据库日志已安全配置。

## 同步频率与新鲜度：必须由负责人确认

**尚无获批正式同步频率，不在此编造数值。** 每条记录的有效截止为：

`E = min(verified_at + SOURCEID_ENTERPRISE_MAX_AGE, valid_until)`

登录、后续 Access 及 SwitchTenant 校验在当前时间达到 E 后拒绝；不因已有绑定、尚未到 Access JWT exp 或本地 Session 期限就继续放行。未来 verified_at、非 active、不同政策、缺失证明或数据库不可用同样拒绝。disabled 增量在同一事务中撤销对应企业 Session 和派生 Token；独立密码登录和其他 Provider 不受定向撤销影响。

设实际同步周期为 P、最大来源传播/交付延迟为 L、重试恢复预算为 R、时钟与告警余量为 M。正式政策需保证常态下 `P + L + R + M < EnterpriseMaxAge`，且下一次成功核验能在 valid_until 前到达。若来源无法承诺该关系，不开启全员业务配置。

上线前按剩余有效时间分布进行预检；设置“最旧成功来源核验时间”“即将到期人数”“同步心跳/积压”“拒绝计数”告警，阈值早于恢复预算。同批大量记录不得在无人监控时同步到期。故障时不得自动放大 max_age 或批量伪造 verified_at；保留安全拒绝，恢复可信同步后按版本更新。

正式待填参数：P、L、R、M、EnterpriseMaxAge、valid_until 策略、停用传播上限、值班及恢复负责人、真实政策引用。60/60/30/60 分钟会话候选不能替代这些目录参数，也不代表普通 SID SSO 会持续检查员工在职。

## JIT及正式一次性开放的补充

正式不进行线上人员灰度。独立测试可以保留pilot模式；正式一次性面向公司全员加载enterprise_all，不使用逐人JSON名单、人数上限或部门/角色限制。历史账号归属核验覆盖公司所有原账号，不以现有3账号副本推定生产完整范围。

JIT复用现有公司级SID企业身份与精确邮箱域配置；需SID/公司负责人确认实际允许的企业账号类型、开户资格及完整正式域集合（可多域），不收集事业部组织属性，不新增组织字段校验。邮箱域清单是企业开户政策，不授予空间/知识权限；新账号无默认权限，公共知识仅按共享ACL开放。

启用JIT政策还必须确认历史账号全量核验的完整性，处理遗漏、邮箱变化与回收异常。不能仅因当前邮箱未命中就宣称已证明没有历史账号；未知历史归属及冲突不得转为新员工开户授予。

JIT新账号仅在严格OIDC与独立批准政策后创建；记录独立的JIT开户来源，不把当前登录写成旧账号历史证明。此类新账号后续可在同一JIT政策下通过新的完整OIDC登录更新其身份快照，Access/Refresh/页面刷新不更新证明或绝对会话期限。disabled、撤销及sub冲突不能由JIT自动恢复。

经权威目录正式接管的新账号，改走统一目录证据及新鲜度规则，不再由JIT自动续接目录证据。普通SSO/JIT身份快照不是实时员工在职证明，其残余风险必须纳入实际审批。
