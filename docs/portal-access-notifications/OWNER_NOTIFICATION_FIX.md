# 多 Owner 通知处理与门户汇总优化

申请通过、拒绝或撤回时，在原业务事务内将该申请发给所有 Owner 的提醒标记为已读，保留历史及原有已读时间。申请人收到的审批结果保持未读。事务失败时，成员授权、申请状态、Owner 提醒与结果通知一起回滚。

通知列表按已授权接收人的关联申请批量补充 `request_status`、`reviewed_by`、`reviewer_name`、`reviewed_at`；再次校验空间 ID，不向其他空间的引用暴露审批信息。已处理提醒展示结果、处理人和时间，并停止跳转到待审批入口。

沿用两分钟轮询，成功轮询会刷新已打开的消息与审批列表，即使未读数量没有变化。窗口重新获得焦点或恢复可见时立即刷新。过期审批页面遇到已处理申请会更新列表；幂等通过不会冒充原审批人。

门户铃铛位于顶部汇总栏，加载失败时仍保留；移动端固定在该栏第一行右侧。普通网页登录用户可查看已发布、有效空间的文档条目数量，汇总与卡片使用同一口径；文档 ID、标题、内容、检索权限及成员身份不随统计公开。上传文件、FAQ/Wiki 等细分统计与受限 API Key 仍沿用原有权限。

## 数据与部署

本次无表结构或迁移版本变更，继续使用 schema 3050。部署时需对历史已通过、已拒绝、已撤回申请的 Owner 提醒做一次已读状态修正，仅匹配 `tenant_access_request` / `access_request_submitted`、相同申请 ID 与空间 ID，不改申请状态或成员授权。保留操作前快照及审计。

回退使用旧应用和前端镜像，不需要数据库降级；已处理提醒的已读修正保留。生产操作及测试通知清理记录保存在私有交付回执中，不提交真实用户数据。

## 回归重点

- 两个 Owner 同时收到申请；任一 Owner 通过或拒绝后，双方提醒退出未读，历史显示实际审批人；申请人的结果通知仍未读。
- 撤回也关闭所有 Owner 的提醒；重复审批不重复授权或发通知；相反审批被拒绝。
- 结果通知失败和撤回提醒更新失败时完整回滚；保留其他请求、其他用户的消息及原已读时间。
- 消息引用不能跨空间泄露审批信息；受限 API Key 不获得新增统计权限。
- 普通用户可见已发布空间的文档总量，但不能访问未授权内容；顶部只显示一个门户铃铛，桌面与移动端均可用。
